# Instrucciones — Auditoría de Base de Datos, Consultas y Rendimiento
### Para ejecutar sobre el código del sistema (migraciones, modelos, controladores y vistas)

**Objetivo:** dejar la base de datos limpia y consistente (migraciones consolidadas, sin campos duplicados ni sobrantes, con llaves foráneas e índices correctos), eliminar consultas ineficientes (N+1, columnas de más) y hacer que el sistema sea rápido y fluido sin sobrecargarse.

**Cómo usar este documento:** es una lista de instrucciones para quien ejecute la auditoría (persona o IA con acceso al código). Está escrito sin depender de un framework específico; donde hace falta, se indica el equivalente en Laravel y en Django. Antes de empezar, confirmar los datos de la sección 0.

---

## 0. Datos previos a confirmar (no empezar sin esto)

- [ ] **Stack y versión:** framework (Laravel, Django u otro) y su versión.
- [ ] **Motor de base de datos:** MySQL/MariaDB, PostgreSQL o SQLite, y su versión (cambia la sintaxis de índices y tipos).
- [ ] **Estado de las migraciones:** ¿ya corrieron en una base con datos reales (producción o pruebas con información que se quiera conservar), o solo en desarrollo?
- [ ] **Respaldo:** existe un respaldo completo reciente de la base de datos antes de tocar nada.
- [ ] **Rama de trabajo:** todo el trabajo se hace en una rama nueva; nada se aplica directamente sobre la principal.

---

## 1. Reglas de seguridad (obligatorias, aplican a todas las fases)

1. **Primero informar, después cambiar.** Cada fase empieza con un informe de hallazgos. Nada se modifica ni se borra hasta que el responsable apruebe el informe.
2. **Nunca borrar una columna o tabla sin evidencia y aprobación.** Cada eliminación propuesta debe traer la prueba de que no se usa (ver sección 2.4) y quedar en una lista aparte para aprobación explícita.
3. **No reescribir migraciones ya ejecutadas en una base con datos que se quiera conservar.** En ese caso se crea una migración nueva de limpieza (ver sección 2.1).
4. **Probar en una copia.** Toda migración consolidada se prueba creando la base desde cero y comparando el esquema resultante con el esquema actual (deben ser equivalentes, salvo lo aprobado).
5. **Cambios pequeños y reversibles.** Un commit por cambio lógico, cada migración con su método de reversa (`down` / reverse) funcional.
6. **No cambiar el comportamiento visible.** Ninguna optimización debe alterar resultados, totales, montos (`C$`) ni el orden esperado de los datos.
7. **No inventar.** Si algo no se puede determinar leyendo el código (por ejemplo, si un campo lo usa una integración externa), se marca como "por confirmar" y no se toca.

## 2. Fase 1 — Base de datos y migraciones

### 2.1 Consolidar migraciones

- [ ] Listar todas las migraciones en orden cronológico y agruparlas por tabla.
- [ ] Identificar las migraciones que solo agregan, modifican o eliminan columnas, índices o llaves de una tabla ya creada (por ejemplo, "agregar columna X a la tabla Y").
- [ ] **Si no hay datos reales que conservar:** fusionar cada una de esas migraciones dentro de la migración de creación de su tabla y eliminar el archivo suelto. Una migración de creación por tabla.
- [ ] **Si hay datos reales:** no reescribir las migraciones ejecutadas. Crear una sola migración nueva de limpieza que aplique índices, llaves y cambios de columnas, y dejar el historial anterior intacto.
- [ ] Respetar el orden de dependencias: una tabla no puede referenciar a otra que se crea después. Reordenar fechas o nombres si hace falta.
- [ ] Al fusionar, **resolver el estado final de cada columna:** si una columna se agregó y luego se modificó (tipo, longitud, nulabilidad, valor por defecto), la migración consolidada usa solo la definición final. Si se agregó y luego se eliminó, no debe aparecer.
- [ ] Verificar que el esquema resultante de la base recién creada coincide con el esquema actual de la base de desarrollo.

### 2.2 Campos duplicados y de igual propósito

- [ ] Detectar columnas repetidas dentro de una misma tabla (mismo nombre agregado dos veces por migraciones distintas).
- [ ] Detectar columnas distintas con el mismo propósito. Ejemplos a buscar: `precio` / `precio_venta` / `price`; `costo` / `precio_compra` / `costo_adquisicion`; `estado` / `activo` / `status`; `nombre` / `descripcion` con el mismo contenido; `stock` guardado en el producto y también calculable desde los lotes.
- [ ] Para cada par, determinar cuál es la fuente de verdad. Proponer unificar; si se unifican, migrar los datos y actualizar modelos, vistas, consultas, reportes y exportaciones que usaban la columna descartada.
- [ ] **Datos derivados guardados:** marcar las columnas que almacenan un valor que se puede calcular (por ejemplo, margen, stock total, subtotales). Proponer eliminarlas o justificar por qué se guardan (rendimiento) y cómo se mantienen sincronizadas.
- [ ] Revisar tipos inconsistentes para el mismo concepto en tablas distintas (ejemplo: dinero como `decimal(12,2)` en una tabla y `float` en otra). Los montos siempre en `decimal`, nunca en `float`.

### 2.3 Llaves foráneas e integridad

- [ ] Toda columna que referencia a otra tabla (`*_id`) debe tener su llave foránea declarada. Listar las que faltan.
- [ ] Cada llave foránea debe cumplir: mismo tipo y signo que la columna referenciada, tabla y columna destino correctas, y una regla `ON DELETE` / `ON UPDATE` deliberada (`restrict` para datos históricos como ventas y compras, `cascade` solo para detalles dependientes, `set null` solo si la columna admite nulos).
- [ ] Verificar relaciones mal vinculadas: llave que apunta a una tabla equivocada, o dos llaves distintas para la misma relación.
- [ ] Detectar **datos huérfanos** existentes (filas cuyo `*_id` no existe en la tabla padre) antes de agregar una llave; informar la cantidad y proponer cómo limpiarlos.
- [ ] Revisar columnas que deberían ser `NOT NULL` y no lo son (y viceversa) según la regla de negocio.
- [ ] Revisar restricciones únicas de negocio que falten: por ejemplo, código de barras de producto, RUC o identificación de proveedor, número de comprobante por serie, correo de usuario, un solo precio vigente por producto y presentación.

### 2.4 Columnas y tablas sobrantes

- [ ] Para cada columna de cada tabla, buscar su uso en: modelos (campos permitidos, relaciones, casts), controladores, servicios, vistas/plantillas, reportes, exportaciones, seeders, factories, pruebas y consultas SQL manuales.
- [ ] Clasificar cada columna: **usada**, **sin uso aparente**, **por confirmar**.
- [ ] Para las "sin uso aparente", entregar la evidencia (búsquedas realizadas y resultado vacío) y revisar si la columna tiene datos. Una columna con datos y sin uso en el código es candidata, pero queda en la lista de aprobación.
- [ ] Revisar también tablas completas sin modelo ni referencias, y tablas pivote o de log que ya nadie lee.
- [ ] **Eliminar solo lo aprobado**, mediante migración con `down` que recree la columna, y después de confirmar que existe respaldo.

### 2.5 Índices

- [ ] Primero listar los índices existentes de cada tabla (incluidos los que crean automáticamente las llaves foráneas y las restricciones únicas) para **no duplicarlos**.
- [ ] Detectar índices duplicados o redundantes (mismo conjunto de columnas, o un índice que es prefijo exacto de otro compuesto) y proponer eliminarlos.
- [ ] Crear los índices que falten, de estos tipos:
  - **Únicos** para las restricciones de negocio (sección 2.3).
  - **De llaves foráneas** donde el motor no los cree automáticamente.
  - **Simples** en columnas usadas con frecuencia en `WHERE`, `ORDER BY` y `JOIN` (estado, fecha, código).
  - **Compuestos** para consultas combinadas frecuentes. El orden de columnas importa: primero las de igualdad, luego rango u orden. Ejemplos del dominio: lotes por (`producto_id`, `fecha_vencimiento`), ventas por (`fecha`, `estado`), movimientos de kardex por (`producto_id`, `fecha`), detalle de venta por (`venta_id`, `producto_id`).
  - **De texto** (`FULLTEXT` o equivalente) solo si hay búsquedas por nombre o principio activo que lo justifiquen; para `LIKE '%texto%'` un índice normal no ayuda.
- [ ] Justificar cada índice nuevo con la consulta que lo necesita. No crear índices "por si acaso": cada uno ralentiza las escrituras.
- [ ] Verificar con `EXPLAIN` que las consultas críticas usan los índices creados.

## 3. Fase 2 — Consultas

### 3.1 Consultas N+1

- [ ] Buscar relaciones accedidas dentro de ciclos o plantillas (por ejemplo, listar ventas y por cada una consultar el cliente, el cajero y los detalles).
- [ ] Corregir cargando las relaciones por adelantado (Laravel: `with()` / `load()`; Django: `select_related()` para uno a uno y llave foránea, `prefetch_related()` para uno a muchos y muchos a muchos).
- [ ] Para conteos y sumas de relaciones, usar agregados en la misma consulta (Laravel: `withCount`, `withSum`; Django: `annotate` con `Count` y `Sum`) en lugar de contar en el ciclo.
- [ ] Revisar especialmente: listados con tablas (ventas, compras, inventario, kardex, lotes, recetas, catálogos), reportes, el POS, el buscador de medicamentos y los tableros con tarjetas.
- [ ] Medir antes y después: número de consultas por pantalla. Herramientas: Laravel Debugbar o Telescope, Django Debug Toolbar, o el registro de consultas del propio framework.

### 3.2 Traer solo los campos necesarios

- [ ] Eliminar `SELECT *` implícito donde la vista usa pocas columnas (Laravel: `select()`; Django: `only()` / `values()` / `values_list()`).
- [ ] Al cargar relaciones, limitar también sus columnas (siempre incluyendo la llave necesaria para unirlas).
- [ ] En listados, no cargar campos pesados (descripciones largas, imágenes en base64, textos grandes, JSON) que la tabla no muestra.
- [ ] En selectores y autocompletado AJAX devolver solo `id`, nombre y el dato secundario que se muestra.
- [ ] En exportaciones y reportes grandes, procesar por bloques (Laravel: `chunk` / `cursor` / `lazy`; Django: `iterator()`) en lugar de cargar todo en memoria.

### 3.3 Optimizar consultas

- [ ] Mover cálculos al motor de base de datos (sumas, promedios, agrupaciones) en vez de hacerlos en el código recorriendo colecciones.
- [ ] Sustituir consultas repetidas dentro de una misma petición por una sola (reutilizar el resultado).
- [ ] Reemplazar subconsultas correlacionadas costosas por uniones o agregados precalculados cuando convenga.
- [ ] Evitar funciones sobre columnas indexadas en el `WHERE` (por ejemplo, `DATE(fecha)`), que impiden usar el índice; usar rangos.
- [ ] Evitar `OFFSET` altos en tablas grandes; usar paginación por cursor o por llave donde aplique.
- [ ] Revisar que los filtros del Index (búsqueda, estado, fechas, categoría, proveedor) se apliquen en la consulta y no sobre la colección ya cargada.
- [ ] Revisar transacciones: operaciones de varias tablas (venta, compra, ajuste de inventario, cambio de precio) deben ir en una sola transacción, con bloqueo cuando se modifica stock para evitar condiciones de carrera.

## 4. Fase 3 — Rendimiento y fluidez del sistema

> **Regla:** antes de agregar cualquier técnica, verificar si ya existe en el sistema. Si ya está implementada, **omitirla** y continuar con la siguiente. Documentar en el informe cuáles ya existían.

- [ ] **Paginación del lado del servidor** en todos los listados y tablas grandes (con tamaño de página razonable y selector de cantidad). Nunca cargar un listado completo para paginar en el navegador.
- [ ] **AJAX para selectores y buscadores** con muchos registros (medicamentos, proveedores, categorías, laboratorios, clientes): búsqueda asíncrona con debounce, mínimo de caracteres y máximo de resultados.
- [ ] **Carga diferida de bloques pesados:** tarjetas de métricas, gráficos y secciones secundarias de reportes y del dashboard se cargan por separado (AJAX o componentes diferidos) para que la pantalla aparezca de inmediato.
- [ ] **Caché de datos que cambian poco:** catálogos (categorías, laboratorios, presentaciones, métodos de pago), configuración y listas de apoyo. Con expiración razonable e invalidación al guardar o editar.
- [ ] **Caché de resultados costosos:** métricas del dashboard y de reportes (ventas del mes, valor del stock, valorización PEPS, top de medicamentos), con tiempo de vida corto o invalidación por eventos. Para cálculos muy pesados, evaluar tablas resumen que se actualicen al registrar movimientos.
- [ ] **Caché de la aplicación en producción** (Laravel: `config:cache`, `route:cache`, `view:cache`, `event:cache`; Django: caché de plantillas y de sesión), OPcache activo en el servidor y modo `debug` desactivado.
- [ ] **Driver de caché y sesiones adecuado:** evitar el driver de archivos si hay carga; usar Redis o Memcached cuando exista.
- [ ] **Trabajos en segundo plano (colas)** para tareas pesadas: exportaciones PDF/Excel/CSV grandes, envío de correos, recálculos masivos y actualización masiva de precios. La pantalla responde de inmediato y avisa al terminar.
- [ ] **Recursos del navegador:** CSS y JS minificados y agrupados, carga con `defer`/`async`, imágenes comprimidas y con carga diferida, compresión gzip o brotli, y encabezados de caché para recursos estáticos.
- [ ] **Interacciones fluidas:** debounce en buscadores, evitar recargar la página completa para acciones simples (usar peticiones AJAX con actualización parcial), estados de carga visibles, y evitar recalcular totales en cada pulsación en formularios grandes (POS, compras).
- [ ] **Búsqueda del POS:** que responda en milisegundos (índices en código de barras y nombre, límite de resultados, y datos mínimos por resultado).
- [ ] **Conexiones y consultas por petición:** revisar middleware, proveedores de servicios y vistas compartidas que ejecutan consultas en **todas** las páginas (menú, notificaciones, contadores de alertas); cachearlas o hacerlas diferidas.
- [ ] **Registro de consultas lentas:** activar el log de consultas lentas del motor y revisar las más frecuentes y las más lentas.

## 5. Entregables

1. **Informe de la fase 1** (antes de modificar): migraciones agrupadas por tabla, columnas duplicadas o equivalentes, llaves foráneas faltantes o mal vinculadas, datos huérfanos, índices existentes, duplicados y propuestos, y lista de columnas/tablas sobrantes con su evidencia.
2. **Migraciones consolidadas** (o migración de limpieza, según la sección 2.1) y evidencia de que el esquema equivale al original, salvo los cambios aprobados.
3. **Informe de la fase 2:** consultas N+1 encontradas y corregidas (con el número de consultas antes y después por pantalla), consultas que traían campos de más, y optimizaciones aplicadas.
4. **Informe de la fase 3:** técnicas que ya existían (omitidas), técnicas agregadas y mejora medida (tiempo de respuesta o número de consultas) en las pantallas críticas.
5. **Lista de pendientes** que requieren decisión del responsable.

## 6. Criterios de aceptación

- [ ] La base se crea desde cero con las migraciones consolidadas, sin errores, y el esquema coincide con el esperado.
- [ ] No quedan columnas duplicadas ni llaves foráneas sin declarar; todas apuntan a la tabla y columna correctas.
- [ ] Ningún índice duplicado; los índices nuevos están justificados y verificados con `EXPLAIN`.
- [ ] Ninguna pantalla principal ejecuta consultas N+1; el número de consultas por pantalla se redujo y está documentado.
- [ ] Los totales, montos en `C$`, stock y reportes dan exactamente los mismos resultados que antes.
- [ ] Las pantallas críticas (POS, listados, dashboard, reportes) responden notablemente más rápido, con medición antes y después.
- [ ] Ninguna columna ni tabla fue eliminada sin aprobación explícita.

## 7. Complementos que se sugiere agregar (no incluidos en tu lista original)

Estos puntos no estaban en las instrucciones iniciales, pero encajan con el objetivo. Revisa cuáles quieres conservar:

- **Respaldo y rama de trabajo obligatorios** antes de empezar (secciones 0 y 1).
- **Datos huérfanos antes de crear llaves foráneas** (sección 2.3): sin esto, la migración falla en una base con datos.
- **Regla `ON DELETE` deliberada** por llave (restrict para historiales, cascade solo para detalles).
- **Dinero siempre en `decimal`** y consistencia de tipos entre tablas (sección 2.2).
- **Restricciones únicas de negocio** (código de barras, RUC, comprobantes, un solo precio vigente).
- **Columnas derivadas guardadas** (margen, stock total, subtotales): decidir si se eliminan o cómo se mantienen sincronizadas.
- **Transacciones y bloqueo en operaciones de stock** para evitar ventas simultáneas sobre el mismo lote (sección 3.3).
- **Consultas ejecutadas en todas las páginas** (menú, alertas, contadores), una causa frecuente de lentitud general (sección 4).
- **Colas para exportaciones y procesos masivos**, y **tablas resumen** para métricas pesadas (sección 4).
- **Log de consultas lentas** y medición antes/después como criterio de aceptación.
